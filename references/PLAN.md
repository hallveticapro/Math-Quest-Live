# MathQuest Live Megabatch Plan - May 2026

This file is the source of truth for the next implementation pass.

Codex must read this file fully before editing, re-read it throughout the work, and use it to prevent requirement drift. This batch touches multiple areas of MathQuest Live, but it is not a redesign. It is a focused polish, replayability, standards-coverage, and classroom-readiness pass.

## Big Picture Goal

MathQuest Live should feel more like a real, replayable classroom-safe math adventure and less like a small set of repeated math generators wrapped in story text.

The current foundation is strong:

- Students use preset choices only.
- The story is AI-assisted but controlled.
- Math is generated and checked by deterministic app code.
- The app is session-only.
- The app avoids accounts, dashboards, reports, analytics, and persistence.

This pass should make the game feel:

- more varied,
- more polished,
- more readable,
- more accessible,
- more standards-complete,
- more replayable,
- and more classroom-safe for Florida elementary use.

The largest and most important part of this batch is math generator expansion. Spend the most time there.

## Product Philosophy

MathQuest Live is intentionally a lightweight, student-facing play experience. It is not an LMS, gradebook, intervention dashboard, classroom management tool, or reporting platform.

The ideal session feels like this:

1. A student enters a safe preset adventure setup.
2. The story gives them an engaging scenario.
3. They choose from button/card-based actions.
4. The app gives deterministic math aligned to the selected challenge band.
5. Correct answers advance the story.
6. The session ends with a satisfying, non-persistent ending/reward.

The game should feel fun enough that students want to replay it, while still being educationally defensible.

## Non-Negotiable Guardrails

Do not add:

- Teacher-facing UI
- Dashboards
- Classroom mode
- Reports
- Analytics
- Student accounts
- Login systems
- Databases
- Saved progress
- Persistent student history
- Persistent achievements
- Cloud saves
- Rosters
- Assignment systems
- Freeform student story input
- Ads
- Any feature that stores student data beyond the active session

Student story interaction must remain:

- preset,
- button/card based,
- classroom-safe,
- age-appropriate,
- and session-only.

Math must remain:

- generated by deterministic app code,
- checked by deterministic app code,
- independent from AI.

AI may only generate:

- story scenes,
- story choices,
- optional controlled images.

OpenAI keys must remain backend-only. The frontend must never receive or use secrets.

## Difficulty and Standards Philosophy

Challenge levels map to Florida B.E.S.T. standards bands:

- Easy / Adventurer = Grade 3 Florida B.E.S.T.
- Medium / Hero = Grade 4 Florida B.E.S.T.
- Hard / Champion = Grade 5 Florida B.E.S.T.
- Extreme / Legend = advanced Grade 5 only.

Do not add a student-facing grade selector.

Extreme should feel harder because it uses deeper Grade 5 reasoning, not because it becomes middle school math.

Extreme may use:

- more steps,
- larger Grade 5-appropriate numbers,
- stronger distractors,
- combined Grade 5 skills,
- less obvious reasoning,
- more strategic problem solving.

Extreme must not use:

- Grade 6 standards,
- negative number arithmetic,
- slope,
- linear equations,
- ratios as a middle-school proportional reasoning unit,
- middle school algebra,
- anything outside advanced Grade 5 expectations.

The goal is advanced elementary, not sixth grade wearing a fake mustache.

# Section 1: Ending Screen and Story Cleanup

## Why This Matters

Recent additions made some story moments feel redundant. The “chronicle remembered…” style recap repeats what already happened and makes the pacing feel awkward. The same issue appears in the outro achievements when they simply restate setup facts like the student’s hero name, quest length, or difficulty.

That kind of text does not feel like a reward. It feels like the app is reading its own settings page out loud.

The story should carry consequence naturally. The ending should feel like a payoff, not a metadata receipt.

## 1A. Ending Story Font Consistency

### Problem

The ending/completion screen story text has regressed to the smaller font size from before. It should match the readable story font size used throughout the main adventure.

### Tasks

- Inspect the story/body text styling used during normal gameplay.
- Inspect the ending/completion/outro text rendering.
- Update the ending story text so it matches the main adventure story text size and readability.
- Do not enlarge unrelated UI elements.

### Do Not Change

- Buttons
- Headers
- Labels
- Badges
- Settings text
- Metadata text
- Navigation controls

### Acceptance Criteria

- Ending story text visually matches the main adventure story text.
- Ending text is readable on mobile and desktop.
- No unrelated UI is enlarged.

## 1B. Remove Redundant Chronicle Recap Text

### Problem

Story screens currently include separate recap-style lines like:

- “The chronicle remembered that Elara chose...”
- “It led to...”
- “The chronicle records...”

This was meant to connect action to consequence, but in practice it feels unnecessary and clunky because the story already includes the consequence.

### Tasks

Remove the separate recap feature from story transitions.

Remove any related:

- UI blocks,
- props,
- helper functions,
- styles,
- generated text fields,
- prompt instructions,
- fallback templates,
- unused types.

Only remove pieces that are specifically supporting the redundant recap behavior.

### Preserve

- Actual story scene text
- Student action choices
- Math challenge flow
- Image flow
- Safe fallback story content
- Natural story consequence inside the scene

### Acceptance Criteria

- No story screen shows a separate “chronicle remembered/chose/led to” recap.
- The story still advances normally.
- The next scene can still naturally mention the result of the selected action.

## 1C. Remove Redundant Outro Achievements

### Problem

Outro achievements that merely restate setup facts are not meaningful.

Examples of weak achievements:

- “You chose a standard adventure.”
- “Your hero was named Elara.”
- “You played on Hero difficulty.”
- “You selected this class/ancestry.”

These are not achievements. They are labels.

### Tasks

- Inspect the ending/completion achievement section.
- Remove achievements that merely restate setup metadata.
- Keep only achievement/reward content that feels meaningful, student-facing, and non-redundant.
- If meaningful story-beat data already exists naturally, Codex may use it.
- If meaningful story-beat data does not already exist, remove the section rather than inventing a tracking system.

### Do Not Add

- Persistent achievements
- Reports
- Analytics
- Saved history
- Databases
- Teacher views
- New tracking systems

### Acceptance Criteria

- Outro does not display filler achievements.
- Ending reward/badge/flavor still feels fun if already supported.
- No persistence or analytics are added.

# Section 3B: Story Scene Question Hook

## Why This Matters

Students pointed out that story scenes feel more natural when they end by clearly inviting the next choice. That is good feedback. The app is a choose-your-own-adventure style experience, so each story scene should naturally tee up the student’s next decision.

Right now, a scene may end with story description but not always make the choice moment feel intentional. A short in-world question at the end helps students understand, “Now it is my turn to decide.”

This should not be a redundant recap. It should be a forward-looking hook.

## Goal

Each playable story scene should end with a brief, flavorful question that points toward the next action choice.

The question should vary naturally and fit the story context.

Examples:

- “What will Zara do next?”
- “Which path should Zara try now?”
- “How will Zara get past the glowing gate?”
- “What is Zara’s next move?”
- “Where should Zara search next?”
- “How should the hero face this challenge?”
- “What is the next step in Zara’s quest?”

The wording should not be identical every time.

## Requirements

- Update story prompt instructions so generated playable scenes usually end with a short question that invites the next choice.
- The question should use the hero’s name when natural.
- The question should match the scene’s genre, tone, and immediate situation.
- The question should be student-friendly and clear.
- The question should be forward-looking, not a recap.
- The question should not mention math, benchmarks, standards, or app mechanics.
- The question should not reveal which choice is correct.
- The question should not be scary, violent, romantic, political, religious, or unsafe.
- Avoid using the exact same sentence every time.
- Fallback story scenes should also include a simple next-step question.

## Do Not Do

Do not add separate recap text like:

- “The chronicle remembered...”
- “Zara chose...”
- “That choice led to...”

Do not add an extra UI block just for this question unless the existing story rendering already supports it naturally.

The preferred behavior is that the story scene text itself ends with the question.

## Acceptance Criteria

- Playable story scenes end with a natural next-step question.
- The question varies across scenes.
- The question fits the scene context.
- The question does not feel like redundant recap text.
- Fallback scenes include a simple next-step question.
- Story choices still appear normally after the scene.

- “Use the reference table below to solve the problem.”

- Keep benchmark codes out of student-facing text.
- Make sure answer choices still include units.

## Acceptance Criteria

- repeated domains,
- repeated templates,
- repeated structures,
- too many similar problems in one session,
- underused standards,
- shallow replayability.

Greatly expand deterministic math coverage across all difficulty bands.

Every feasible Florida B.E.S.T. benchmark marked as potential for expansion should be implemented with multiple variations and complexity levels.

This should not be token coverage.

Do not add one problem template and call a benchmark done if the standard can reasonably support more.
